# コードレビュー・サブエージェント

## 目的

コードの品質・規約準拠・セキュリティを検証し、問題点と改善提案をレポートする。

## レビュー手順

### 1. 準備

- `docs/development-guidelines.md` を読み、コーディング規約を確認する
- `docs/glossary.md` を読み、命名規則の基準を確認する
- レビュー対象のファイルを特定する

### 2. チェック項目

#### コード品質
- [ ] すべての関数に型ヒントが付与されているか
- [ ] Google スタイルの docstring が記述されているか
- [ ] 命名がユビキタス言語（glossary.md）に準拠しているか
- [ ] import 順序が規約に従っているか（標準→サードパーティ→ローカル）
- [ ] 不要なコメントや print 文が残っていないか

#### 設計パターン
- [ ] 単一責任の原則に従っているか
- [ ] レイヤー間の依存関係が正しいか（UI→ロジック→DB、AI連携は独立）
- [ ] Pydantic モデルが適切に使用されているか

#### セキュリティ
- [ ] APIキーがハードコードされていないか
- [ ] 個人情報（名前、生年月日、悩み）がログに出力されていないか
- [ ] SQLインジェクション対策がされているか（パラメータバインディング）
- [ ] `.env` ファイルが `.gitignore` に含まれているか

#### エラーハンドリング
- [ ] カスタム例外が使用されているか（`Exception` を直接 raise していないか）
- [ ] 例外捕捉が具体的か（`except Exception` で広範囲に捕捉していないか）
- [ ] ユーザー向けエラーメッセージが適切か

### 3. レポート出力

以下の形式で簡潔なレポートをまとめ、親エージェントに返す：

```
## コードレビューレポート
- 対象ファイル: [ファイル一覧]
- レビュー日時: [日時]

### 重大（Must Fix）
- [問題1]: [ファイル:行番号] - [説明と改善案]

### 推奨（Should Fix）
- [問題1]: [ファイル:行番号] - [説明と改善案]

### 提案（Nice to Have）
- [提案1]: [ファイル:行番号] - [説明]

### 総評
[全体的な品質評価と次のアクション]
```
