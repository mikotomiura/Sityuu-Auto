# /fix-bug — バグ修正ワークフロー

バグを修正する際の完全なワークフロー。再現確認→原因特定→修正→回帰テストの順に実行する。

---

## 1. バグの理解

1. バグの報告内容（症状・再現手順・期待動作）を確認する
2. `CLAUDE.md` を読み、プロジェクトの作業ルールを確認する

## 2. 構造化ノートの作成

`.steering/[YYYYMMDD]-fix-[バグ概要]/` ディレクトリを作成し、以下を初期化：

- `requirement.md` — バグの症状、再現手順、期待される修正後の動作を記述
- `tasklist.md` — 空のテンプレートを配置

## 3. 再現の確認

1. 報告された再現手順に従い、バグを再現する
2. 再現できた場合：エラーメッセージ・スタックトレースを `requirement.md` に記録
3. 再現できない場合：環境差異や前提条件を確認し、追加情報を収集

## 4. 原因の特定

1. エラーメッセージ・スタックトレースから、関連するファイルを特定
2. `Grep` で関連コードを検索
3. **サブエージェント `file-finder` を起動** し、関連ファイルを網羅的に特定
4. 根本原因を特定し、`.steering/[今回]/design.md` に記録

原因調査のチェック項目：
- 入力データのバリデーション漏れか
- 型の不一致か
- 例外処理の不足か
- 状態管理（`st.session_state`）の問題か
- 外部API（LLM）のレスポンス形式変更か
- DB スキーマとモデルの不一致か

## 5. 影響範囲の確認

1. **サブエージェント `impact-analyzer` を起動** し、修正の影響範囲を確認
2. 修正によって壊れる可能性のある箇所をリストアップ
3. タスクを `tasklist.md` に記載

## 6. 修正の実施

1. **まず失敗するテストを書く**（TDD アプローチ）
   - バグを再現するテストケースを `tests/` に追加
   - テストが失敗することを確認
2. コードを修正する
   - `docs/development-guidelines.md` の規約に従う
   - 最小限の変更に留める（関係ない変更を混ぜない）
3. テストが通ることを確認する

## 7. 回帰テスト

1. **サブエージェント `test-runner` を起動** し、全テストを実行
2. 修正によって他のテストが壊れていないことを確認
3. **サブエージェント `test-analyzer` を起動** して結果を分析

## 8. レビュー

1. **サブエージェント `code-reviewer` を起動** してコードレビュー
2. 修正内容が最小限かつ適切か確認
3. 同類のバグが他に潜んでいないか確認

## 9. ドキュメント更新

1. `.steering/[今回]/tasklist.md` を完了に更新
2. バグの原因が設計上の問題であれば、`docs/` の該当ドキュメントを更新

## 10. コミット

```bash
git add .
git commit -m "fix(<scope>): <修正内容の要約>

<バグの根本原因と修正方法の詳細>"
```
