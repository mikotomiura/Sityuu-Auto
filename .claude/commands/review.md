# /review — コードレビューワークフロー

コード変更のレビューを実施する際のワークフロー。品質・セキュリティ・パフォーマンスの観点で検証する。

---

## 1. レビュー準備

1. `docs/development-guidelines.md` を読み、コーディング規約を確認
2. レビュー対象の変更ファイル一覧を確認
3. 関連する `.steering/` のノートがあれば読み、変更の意図を理解

## 2. コード品質レビュー

**サブエージェント `code-reviewer` を起動** し、以下を検証：

- 型ヒントの網羅性
- docstring の記述
- 命名規則（`glossary.md` 準拠）
- import 順序
- エラーハンドリングの適切さ
- 単一責任の原則

## 3. セキュリティレビュー

**サブエージェント `security-checker` を起動** し、以下を検証：

- APIキーのハードコード
- 個人情報のログ出力
- SQLインジェクション対策
- `.env` の `.gitignore` 登録

## 4. テスト品質レビュー

**サブエージェント `test-analyzer` を起動** し、以下を検証：

- 新規コードに対するテストの存在
- テストカバレッジの目標達成
- テストケースの命名規則
- 境界値・異常系テストの網羅性

## 5. パフォーマンスレビュー

手動で以下を確認：

- 不必要なDB呼び出しがないか
- Streamlit の `@st.cache_data` / `@st.cache_resource` が適切に使われているか
- N+1 クエリが発生していないか
- 大量データの処理にページネーションが適用されているか

## 6. レビュー結果のまとめ

各サブエージェントのレポートを統合し、以下の形式でまとめる：

```
## 統合レビューレポート

### 判定: 承認 / 条件付き承認 / 要修正

### Must Fix（修正必須）
1. ...

### Should Fix（修正推奨）
1. ...

### Nice to Have（提案）
1. ...

### Good Points（良い点）
1. ...
```
